# 착수 — 대장을 거치지 않는 일은 없다

새 디렉토리를 손으로 만들면 두 달 뒤 그게 무엇이었는지 아무도 모른다. 실제로 그렇게 됐다:
`temp/`에 161,298 파일 32GB가 쌓였고 그 안에 납품 건 5개가 섞여 있다. 같은 대상(한 거래처)이
5곳에, 같은 종류의 작업(FOC validation)이 8곳에 흩어졌다.

**이 스킬은 그것을 시작 시점에 막는다.** 5분이 든다.

## 0. 중복 확인 — 이게 첫 번째다

새 건이라고 생각한 것이 대개 기존 건의 다른 이름이다.

```bash
cd ~/claude_work
grep -in "<대상명>\|<IMO>\|<화주명>" LEDGER.md
find . -maxdepth 3 -type d -iname '*<대상>*' -not -path '*/.venv/*' -not -path '*/.git/*'
```

**하나라도 걸리면 새 건이 아니다.** 기존 건을 열거나, 그 건의 후속으로 하위에 만든다.
질의 폴더의 두 건(7월 말 → 8월 초)이 좋은 예다 — 같은 원인의 두 번째 발현을 별건으로
두되 서로를 참조하고, 미결은 묶어서 제기하도록 대장에 적었다.

## 1. 분류 판정 — 결과물이 누구에게 가는가

| 답 | 분류 | 어디에 |
|---|---|---|
| 여러 건이 계속 소비할 자산이다 | `platform` | 기존 플랫폼 저장소 안. **새로 만들지 마라** |
| 한 대상·한 질문에 대한 판정이고 납품이 있다 | `case` | `cases/YYMMDD_<대상>_<요지>/` |
| 외부에서 들어온 질의에 회신한다 | `inquiry` | `inquiry/YYMMDD_<질문자>_<요지>/` |
| 며칠 쓰고 버린다 | `scratch` | `scratch/` — **30일 후 승격 또는 삭제** |

애매하면 `case`다. `scratch`는 "버릴 것이 확실한 것"이지 "아직 모르겠는 것"이 아니다.
그 혼동이 `temp/` 32GB를 만들었다.

**`platform`에 새 디렉토리를 만드는 것은 거의 항상 틀렸다.** 건별 산출물을 공용 저장소에
쓰면 다음 사람이 어느 것이 납품물인지 모른다. 잘 정리된 건들이
「공용 자료 저장소는 읽기 전용, 산출물은 저장소 밖」을 README에 명시한 이유다.

## 2. 착수 3결정 — 코드보다 먼저

`analysis-asset-kit/references/bootstrap.md`의 규범. **빈칸을 남기지 마라. 빈칸은 영원히 안 채워진다.**

| 결정 | 안 정하면 |
|---|---|
| **입력 정본** | 같은 수치의 출처가 둘이 되고 어느 쪽이 맞는지 모르게 된다 |
| **비교 기준(basis)** | 괴리가 실재인지 기준 결함인지 판정 불가 |
| **`embed_scale`** | 폰트 하한이 안 정해져 도면을 나중에 전부 다시 그린다 |

`embed_scale`은 산출물 형태로 결정된다 — 도면이 곧 페이지면 `1.0`, 리포트 본문 삽입이면
실제 삽입 배율의 **최솟값**(흔히 0.72~0.95).

## 3. 골격 생성

```bash
CASE=~/claude_work/cases/YYMMDD_대상_요지
mkdir -p "$CASE"/{scripts,input_files,evidence,results,exports,figures,docs/knowledge}
```

`docs/knowledge/`가 **gitignore 대상이 아닌지 확인한다.** 평결이 무시 대상 폴더에 있으면
결론이 사라진다.

## 4. `README.md` — 첫 커밋에 존재해야 한다

```markdown
# YYMMDD_<대상>_<요지>

<대상 식별: 선명 · IMO · 선급/화주 · 관련 계약>
<질문 한 문장: 무엇을 판정하려는가>

## 한 줄 결론

<착수 시점엔 "판정 전". 결론이 나오는 즉시 여기부터 고친다>

## 정본 (SSOT)

- **입력**: <경로> — 불변, 수정 금지
- **1차 산출**: <경로> — 생성 스크립트 <경로>
- **결론·판정**: `docs/knowledge/*.md`

## 기준 (basis)

- 비교 대상: <계약/사양/시운전/타 계측>
- `embed_scale`: <값>

## 공용 자산 취급

- 공용 자료 저장소(platform)는 **읽기 전용**. 쓰지 않는다.

## 파일

| 파일 | 내용 |
|---|---|
```

**한 줄 결론을 "판정 전"으로 두는 것은 허용되지만 비워 두는 것은 아니다.**
좋은 완성 예: 「STW 는 결측 · 스파이크가 아니라 배율/영점이 틀렸다」처럼 한 줄 결론이 판정인 README.

## 5. 대장 등재 — 마지막이 아니라 지금

`~/claude_work/LEDGER.md`의 해당 분류 표에 행을 추가한다.

```
| `cases/YYMMDD_대상_요지/` | <대상> | <요지> | 진행중 | `docs/knowledge/` | MM-DD |
```

상태 어휘는 `LEDGER.md` 맨 아래 표를 따른다. 착수 시점은 항상 `진행중`.
**`미확인`으로 만들지 마라** — 그건 과거 건에만 쓰는 값이고, 갚아야 할 빚이다.

## 6. 이후

- 결론이 나오면 **README 한 줄 결론과 대장 상태를 같은 커밋에서** 고친다. 따로 하면 어긋난다.
- 세션 종료 시 `.ops/harvest_enqueue.sh`가 수확 큐에 적재한다. 다음 세션 시작에 뜬다.
- 승격 판정은 `analysis-asset-kit/references/harvest.md`.

## 하지 않는 것

- **탐색 5분짜리 질문에 골격을 만들지 마라.** 답하고 끝낼 일이면 이 스킬은 과하다.
  기준: 산출물이 남는가, 남는다면 남의 눈에 띄는가. 둘 다 아니면 그냥 답한다.
- **기존 건의 후속을 새 최상위 건으로 만들지 마라.** 0단계가 이걸 잡는다.
