# 대규모 분석 프로젝트 운영

15척 함대 계약검증(두 달, 4개 세션 병행, 산출물 수십 종)을 운영하며 겪은 실패와 그 방지책.
**계산이 틀려서 다시 한 적은 거의 없고, vintage와 출처 관리가 무너져서 다시 한 적은 많았다.**

## 요지

분석 프로젝트가 커지면 적이 바뀐다. 초반의 적은 "계산이 맞는가"지만, 중반 이후의 적은
**"지금 이 숫자가 어느 시점의 어느 기준에서 나온 것인가"** 다. 산출물이 열 개를 넘어가는
순간부터는 정본 규율과 신선도 관리가 분석 자체보다 중요해진다.

## SSOT — 하나의 수치는 하나의 파일에서

- **같은 물리량이 여러 산출물에 나오면 반드시 어긋난다.** 리포트 본문·워크북·요약표가 각자
  계산하지 말고 **단일 파일을 읽는 리더 함수 하나**를 통과하게 하라.
- **서술과 계산이 이원화되면 특히 위험하다.** 문서에는 A 기준이라 써 있는데 계산은 B 기준으로
  도는 상태를 실제로 겪었다. 서술도 같은 리더에서 값을 받아 쓰게 만들어라.
- **본문 생산자가 여러 파일에 흩어져 있을 수 있다.** 우리는 생산자가 3곳이었는데 2곳만 grep해서
  하나를 놓쳤다. 생산자 목록을 문서화하고 변경 시 전수 grep.
- **총계를 정본으로 덮어쓸 때 분해 성분도 같이 갱신하라.** 총계만 바꾸면 성분을 곱해도 총계가
  안 나온다(각주가 옛 기준 값을 인용하던 실사례). 성분과 총계는 같은 행에서 읽는다.
- **식별자(IMO · 선체번호 · 계기 ID)는 설정에서 읽고 손으로 적지 마라 — 일회성 검사 스크립트도.**
  동급선이 여럿인 함대에서 한 자리 틀린 IMO 는 **자매선의 그럴듯한 자료**를 읽는다. 오류가 안 나고
  숫자도 물리 범위 안이다. 실측: 흘수 대조 검사에서 자매선을 읽어 항차가 거꾸로 보였고, 성능
  도면과 어긋나서야 알았다. **이유:** 식별자 오류는 값 검사 게이트를 전부 통과한다 — 막을 곳은
  입력 지점 하나뿐이다.
- 결론은 **gitignore 대상 폴더에 두지 마라.** 산출물 트리가 무시 대상이면 평결 문서는 반드시
  추적되는 문서 폴더(`docs/knowledge/` 등)에 쓴다.

## 신선도(stale) — 성공 로그는 거짓말을 한다

- **`[OK]`는 프로세스가 돌았다는 뜻이지 파일이 갱신됐다는 뜻이 아니다.** 실제 사고 3종:
  ① 생산 코드를 고치고 재실행을 안 해 산출물이 이틀 전 것 ② 플래그를 빠뜨려 **다른 디렉토리**에
  쓰였는데 로그는 그대로 OK ③ 빌드 성공인데 파일이 깨져 있음.
- **검증은 mtime + 소비처 grep으로.** "이 산출물을 소비하는 코드가 어디인가"를 먼저 찾고,
  그 소비처가 읽는 경로의 mtime을 확인한다.
- **입력 mtime > 산출물 mtime이면 FAIL**인 신선도 게이트를 만들어라.
- **하류 재생성은 마지막에 한 번만.** 정본을 움직일 수 있는 작업을 전부 끝낸 뒤 일괄 재생성해야
  중간 vintage가 남지 않는다.

## 변경 통제 4단계

파이프라인 입력·상수·기준선을 바꾸는 모든 변경은 이 순서를 밟는다.

1. **기존값과 비교** — 변경 전/후를 같은 척도로 측정하고, **변하지 않아야 할 대조군**을 두어
   `0.000`을 확인한다. 변경이 의도한 대상에만 닿았음을 이걸로 증명한다.
2. **무엇이 더 정확한지 검토** — "더 재현 가능하다"와 "더 정확하다"는 **다른 주장**이다.
   정확도 우위를 주장하려면 독립 기준에 대한 점수 비교가 있어야 하고, 없으면 없다고 명시한다.
3. **적용 전 승인** — 측정 결과를 먼저 보고하고 승인받은 뒤 반영한다.
4. **문서·기록 전면 동기화** — 코드뿐 아니라 정본 문서, 계보(LINEAGE), 회귀 테스트 핀,
   리포트 본문 수치까지 같은 vintage로 맞춘다.

**어느 부분도 outdated로 남기지 않는다**가 원칙이다. 감사 추적이 곧 신뢰성인 작업에서는
문서와 산출물의 vintage가 어긋나면 결론 자체를 방어할 수 없다.

## 병행 세션·협업자와 한 저장소를 공유할 때

- **다른 세션의 산출물은 읽기와 복사만. 수정하지 않는다.** 필요한 것은 독립적으로 생성한다.
  공유 생산 코드를 고치면 ① 상대의 in-flight 작업을 조용히 덮고 ② 방어 장치가 추가로 필요해지며
  ③ "독립 분석"이라는 산출물의 성격이 흐려진다.
- **수정 대신 출력 열을 소비하라.** 공유 함수에 파라미터를 주입하는 대신, 그 함수가 이미
  내보내는 열을 받아 내 계산을 얹으면 규칙이 **데이터로 상속**된다(재현 오차 0.0 확인).
  단일 출처성이 오히려 좋아지고 생산 접촉면은 0이 된다.
- **커밋은 경로를 명시해 스코프를 한정.** `git add -A`는 남의 미커밋 작업을 함께 담는다.
- **레이스는 mtime 타임라인으로 진단한다.** 내 빌드 시각과 상대 산출물의 갱신 시각을 나열하면
  어느 산출물이 옛 상태를 물었는지 바로 보인다. 상대 변경이 정착한 뒤 **한 번만** 재빌드.
- 읽기 의존(기준표·정본 CSV)은 독립성을 해치지 않는다. 대조 대상은 읽어야 한다.

## 입력 자산 지식화

- **원본 문서를 열기 전에 읽을 digest를 만들어라.** 문서별 요약 + 페이지 참조 + 알려진 quirk +
  미결 항목을 담은 source wiki를 두고, 원본 접근 전 반드시 그것을 먼저 본다. 같은 문서를
  세션마다 다시 해독하는 비용이 사라진다.
- **quirk는 반드시 근거와 함께.** 위키에 적힌 "이 문서는 값이 부풀려져 있음" 같은 메모가
  오독이었던 적이 있다. 정정할 때는 근거(열 비교 등)를 남겨라.
- 원본 입력은 **불변(immutable)** 으로 다루고 파생물만 생성한다.

## 산출 트리 계층화

- **production / diagnostic / archive를 물리적으로 분리**한다. 진단용 산출물이 생산 경로에
  섞이면 어느 것이 납품물인지 모르게 된다.
- 납품 경계를 스크립트로 강제하라(중간 산출물을 `_work/`로 이동시키는 등). 손으로 정리하면
  다음 빌드에서 되돌아온다.
- 파일 해석 규칙(어떤 이름의 파일을 어디서 찾는가)은 **레지스트리 한 곳**에 모은다. 경로
  하드코딩이 흩어지면 입력이 바뀔 때 전수 수정이 필요하다.

## 캐시 설계

- **무거운 입력은 프레임 단위로 캐시**해 두면 재실험이 초 단위가 된다. 우리는 곡선 생성 프레임을
  캐시해 두어 재산출 실험을 척당 수 초에 돌렸고, 캐시로 재계산한 값이 정본과 **30/30 ±0.000%**
  일치함을 게이트로 확인했다.
- **캐시 지문(fingerprint)에 분석 코드 해시까지 넣어라.** 데이터만 지문에 넣으면 코드를 고쳐도
  캐시가 히트해 옛 결과가 나온다.
- 캐시 재사용으로 "바이트 동일"이 나오면 그건 검증이 아니라 **캐시가 작동했다는 증거**일 뿐이다.
  진짜 재현 검증은 캐시를 비우고 한 번 돌려야 한다.
- **외부 조회로 채우는 표는 응답을 `evidence/`에 정본으로 저장하고, 조회가 실패하면 축소가
  아니라 저장본을 쓰게 하라.** 산출물 코드가 "조회 실패 → 오프라인 기본값"으로 조용히
  물러나면 표가 1,139행에서 42행으로 줄고, 그 42행은 **완전한 목록처럼 읽힌다.**
  결측이 아니라 축소라서 어떤 검사도 안 걸린다. 저장본을 쓸 때는 **언제 받은 것인지를
  산출물 안에 적는다** — 그게 없으면 신선도를 되짚을 방법이 없다.
  이건 성능 최적화가 아니라 **완전성 방어**다. 벤더가 도메인을 옮기거나 자격증명을 바꾸면
  조회는 예고 없이 죽는다.

## 작업 중량 조절

- **탐색적 분석(EDA)·일회성 산출물은 인라인으로 직접 쓰고 결과 보며 반복**한다.
  360줄짜리 분석 스크립트에 설계문서 → 태스크 분해 → 서브에이전트 구현/리뷰 12회를 적용했다가
  토큰의 80% 이상을 절차에 쓴 적이 있다.
- 중량 프로세스(정식 계획·다단계 리뷰·서브에이전트)는 (a) 여러 독립 파일을 병렬로 건드리거나
  (b) 회귀 위험이 큰 생산 코드거나 (c) 명시적 요청이 있을 때만.
- **위임할 때는 "네 최종 메시지가 곧 결과물"임을 명시하라.** 지시가 모호하면 에이전트가
  작업만 하고 보고를 반환하지 않아 토큰만 태운다(실제로 3회 겪음).
- **검증 세션인지 구현 세션인지 스스로 명시**하라. 막힌 작업의 전체 스펙을 미리 쓰는 것보다
  **무엇에 막혀 있는지 기록**하는 편이 가치 있다.

## 기존 자산 재사용

- **검증된 모듈이 있으면 알고리즘 자체를 재사용**한다. 스타일만 베끼고 계산을 자작하면 결과가
  비일관해지고 신뢰를 잃는다.
- 새 산출물 형식을 만들기 전에 **기존 산출물의 실제 이미지를 눈으로 확인**하고 그 생성
  스크립트를 재현하라. 형식도 재사용 대상이다.

## 결론의 내구성

- 판정이 나오면 **평결 문서를 추적되는 경로에 쓰고**, 재논의 불필요 항목과 미결 항목을 분리해
  적어둔다. 다음 세션이 같은 논쟁을 반복하지 않는다.
- 미결은 **왜 미결인지(무엇이 있어야 결판나는지)** 를 함께 적는다. "대조 실험 X 없이는 배제 불가"
  같은 형태가 좋다.
